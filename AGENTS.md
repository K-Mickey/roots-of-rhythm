# Swing Music Story — инструкции для ИИ-агентов

## Назначение

Этот файл — обязательная точка входа для opencode. Проект развивается по Spec-Driven Development: требования и контракты определяют ожидаемое поведение, код реализует их, а тесты проверяют.

Пока архитектура и стек не зафиксированы, не выдумывать их. Зафиксировать значимое решение в ADR и получить подтверждение пользователя до необратимой или дорогостоящей реализации.

## Порядок работы

1. Прочитать задачу и связанные материалы в `docs/specs/`.
2. Прочитать применимые правила из `.opencode/rules/`.
3. Исследовать существующий код и найти уже используемые решения.
4. Для нетривиальной функции уточнить требования и критерии приёмки до реализации.
5. Внести минимальное целостное изменение в правильном слое.
6. Выполнить подходящие проверки из `docs/development.md`.
7. Просмотреть diff и сообщить, что изменено, что проверено и что проверить не удалось.

## Источники истины

При конфликте использовать приоритет:

1. Явная текущая команда пользователя.
2. Утверждённая спецификация в `docs/specs/`.
3. API-контракт в `docs/api/`.
4. Принятый ADR в `docs/decisions/`.
5. Правила проекта в `.opencode/rules/`.
6. Существующий код и тесты.

Не менять тесты или документацию, чтобы скрыть расхождение реализации с более приоритетным источником.

## Обязательные ограничения

- Не создавать ветки, коммиты, теги, merge request или pull request без явной команды пользователя.
- Не выполнять production-write операции без плана и явного подтверждения пользователя.
- Не удалять и не перезаписывать пользовательские изменения.
- Не изменять тесты без явного подтверждения пользователя.
- Не отключать линтеры, проверки типов, тесты, security-проверки или pre-commit hooks ради прохождения проверки.
- Не добавлять зависимость, сервис, очередь, кэш, поисковый индекс или графовую БД без подтверждённой необходимости.
- Не публиковать секреты и не записывать их в репозиторий, логи или ответы.
- Не утверждать, что проверка пройдена, если она не запускалась или завершилась ошибкой.
- Не менять публичный контракт без синхронного обновления спецификации, changelog и проверок контракта.

## Spec-Driven Development

Рабочий поток:

```text
идея/ТЗ → спецификация → уточнения → story → декомпозиция → контракт/ADR → реализация → проверка → review
```

Перед реализацией нетривиальной функции должны быть определены:

- цель и пользовательская ценность;
- функциональные и нефункциональные требования;
- критерии приёмки;
- границы задачи и явно исключённые сценарии;
- ошибки, права доступа и данные на границах доверия;
- изменения публичных контрактов и миграций.

Если обязательной информации нет и безопасное предположение изменит продуктовый смысл, остановиться и запросить решение.

## Правила проекта

Все файлы `.opencode/rules/*.md` обязательны в своей области применения и подключены через `instructions` в `opencode.json`. Особенно:

- `llm-behavior.md` — поведение и автономность агента;
- `clean-architecture.md` и `repo-boundaries.md` — архитектурные границы;
- `tests-require-confirmation.md` — строгий запрет правок тестов без подтверждения;
- `prod-changes-require-confirmation.md` — production-безопасность;
- `documentation.md` — SDD и синхронизация контрактов.

## Навыки и команды

Навыки находятся в `.opencode/skills/` (каждый — каталог с `SKILL.md`, frontmatter `name` и `description`). Команды находятся в `.opencode/commands/`. opencode также нативно поддерживает `.agents/skills/`.

Если пользователь вызывает `/имя-команды`, прочитать соответствующий файл команды в `.opencode/commands/` и выполнить его как workflow. Условия запуска навыка обязательны: отсутствие условия означает остановку, а не обход проверки.

## Инструменты

- `ast-index` — локальный AST-индекс кода (структурный поиск по символам, вызовам, импортам, классам). При работе с кодом предпочитать `ast-index outline/search/class/refs/usages` чтению больших файлов целиком; после правок обновлять индекс: `ast-index update`. Подробности — в `.opencode/rules/ast-index.md`.
- `rtk` — bash-хук, сжимающий вывод команд (`git`, `cargo`, `pytest` и др.), экономя токены. Результаты приходят в компактном виде.
- `graphify` — knowledge graph проекта в `graphify-out/` (`graph.html`, `GRAPH_REPORT.md`, `graph.json`). Для вопросов по архитектуре и связям между сущностями предпочитать `graphify query/path/explain` чтению файлов подряд.
- `ponytail` — режим «ленивого старшего разработчика»: писать только необходимое, переиспользовать stdlib и существующий код. Регулируется командами `/ponytail`.

## GitHub tracker

- `docs/specs/` определяет требования; GitHub Issues/Projects отражает исполняемую работу и не переопределяет specification.
- Для полного bootstrap/reconciliation использовать `sync-github-tracker`; для задач одной утверждённой декомпозиции — `create-tracker-tasks`.
- Перед внешней записью выполнить read-only inventory, показать точный dry run и получить явное подтверждение batch.
- Сопоставлять items по стабильным requirement/task IDs и source links; не создавать дубликаты при повторном запуске.
- Не закрывать, не удалять, не архивировать и не перемещать существующие items без отдельной явной команды.
- При ручном расхождении tracker и specification остановить конфликтующий item и запросить решение; не перезаписывать данные догадкой.
- После успешной записи сохранить двусторонние links и проверить фактическое состояние tracker.
