# Clean Architecture

> Границы домена, application-слоя и инфраструктуры

- Направлять зависимости от внешних слоёв к домену.
- Не импортировать HTTP, ORM, UI и конкретные SDK в доменную логику; `msgspec` для domain structures — единственное явно принятое исключение.
- Размещать orchestration и транзакционные границы в application/use-case слое.
- Сохранять связный lifecycle одного aggregate в application service; выделять отдельный use case только при самостоятельном сценарии или отличающихся зависимостях, правах, транзакции либо заметной сложности.
- Для сложного чтения предоставлять предметный public reader внутри context-владельца; reader возвращает read DTO, пакетно загружает собственные данные и не становится универсальным `get_everything`.
- Внедрять в operation только используемые ports. Целевая ответственность UoW — write-транзакция, а не registry repositories; существующий registry-style код мигрировать инкрементально по ADR-0008.
- Выносить mapper/projector в чистую функцию, когда это отделяет I/O от сборки DTO; не создавать обязательный класс без дополнительной ответственности.
- Валидировать в ближайшей правильной границе: transport — форму, use case — сценарий и права, aggregate — инварианты, БД — целостность.
- Размещать работу с БД, сетью, файлами и внешними API в infrastructure-адаптерах.
- Не использовать API DTO и ORM-модели как доменные сущности.
- Не создавать интерфейс с одной реализацией без реальной границы подмены.
- Не добавлять слой, фабрику или абстракцию «на будущее».
- Исправлять нарушение в общем правильном слое, а не дублировать обходы в вызывающем коде.
