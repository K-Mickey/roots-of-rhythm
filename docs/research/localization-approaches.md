# Исследование подходов к локализации

Статус: `research — deferred; не входит в EPIC-001`

Дата проверки: 2026-08-16.

Цель: выбрать стартовый подход к локализации интерфейса и редакционного контента без привязки к конкретному frontend/backend framework.

## Две разные задачи

### Интерфейс приложения

Кнопки, заголовки, сообщения об ошибках и шаблоны дат не являются историческим контентом. Их рекомендуется хранить в version-controlled resource bundles по стабильным message keys и проверять вместе с кодом.

### Редакционный контент

Название Genre, определение, описание формирования и объяснение исторической связи создаются и публикуются редактором. Эти значения рекомендуется хранить на backend как типизированные языковые варианты доменного объекта.

Смешивание двух задач в одной общей таблице переводов ухудшает ограничения данных, поиск, review и аудит публикации.

## Принятые в индустрии варианты хранения контента

### Полная строка сущности на каждую локаль

Пример: таблица `genre` получает составной ключ `(logical_genre_id, locale)`, а period, status и остальные поля повторяются для каждого языка.

Плюсы: чтение одной локали без join; строка выглядит самодостаточной.

Минусы: дублируются языконезависимые данные и внешние связи; изменение периода или статуса требует синхронного обновления нескольких строк; копии могут разойтись.

Вывод: отвергается. Это не предлагаемый проекту вариант.

### Отдельные колонки `name_ru`, `name_en`

Плюсы: минимальный код для двух заранее известных языков.

Минусы: каждая новая локаль меняет схему; сложно одинаково обрабатывать все переводимые поля; появляются условные проверки для каждого языка.

Вывод: не рекомендуется для проекта, который сознательно начинает с локализации.

### JSON со всеми переводами внутри объекта

Плюсы: быстрое прототипирование и отсутствие join.

Минусы: слабее ограничения обязательных полей и уникальности; сложнее индексировать и искать по отдельной локали; field-level review и публикация требуют собственного механизма поверх JSON.

Вывод: допустимо для небольшого прототипа, но не является рекомендуемой основой исторического каталога.

### Типизированная translation entity

Пример концептуальной структуры:

```text
genre
├── id PK
├── period and other language-neutral metadata
└── one row per logical Genre

genre_translation
├── genre_id FK → genre.id
├── locale
├── name
├── definition
├── origin_context
├── characteristic_features
├── formation_narrative
└── publication state

UNIQUE (genre_id, locale)
```

В `genre_translation` не копируются period, relations, Evidence, MediaAsset links и общая identity. Составная пара является естественным ограничением уникальности, но не обязана быть primary key: при отдельном аудите можно использовать surrogate `translation_id` и оставить `UNIQUE (genre_id, locale)`.

Плюсы: уникальность `(genre_id, locale)`, понятные поля и индексы, независимое review языковых вариантов, расширение списка локалей без колонок на каждый язык.

Минусы: один дополнительный join при чтении сущности, своя translation-таблица для каждого типа локализуемого aggregate и необходимость явно определять fallback. Repository или read model скрывает сборку, но не отменяет стоимость запросов и правил публикации.

Вывод: основной кандидат для Swing Music Story, но физическая схема ещё не принята.

### Один JSON-документ на локаль

Гибридный вариант:

```text
genre_content
├── genre_id
├── locale
├── content JSONB
└── publication state
```

В JSON хранится весь локализованный документ Genre, но языконезависимый Genre остаётся отдельным. Это не EAV: одна строка представляет целый языковой вариант с версионируемой schema приложения.

Плюсы: удобно читать и версионировать страницу целиком; меньше SQL-колонок при часто меняющихся секциях.

Минусы: база слабее контролирует обязательность и типы вложенных полей; точечный поиск требует JSON indexes; частичные обновления и миграции content schema сложнее типизированных колонок.

Вывод: реальный кандидат, если Genre page будет развиваться как редакционный документ, а не как набор стабилизированных полей.

### Отдельный Content/Document aggregate

Genre хранит каталоговую identity и структурированные факты, а локализованный текст страницы принадлежит отдельному `LocalizedDocument` или headless CMS и ссылается на GenreId.

Плюсы: сильное разделение каталога и редакционного документа; готовые версии, workflow и rich text; локализация не создаёт translation-таблицу у каждого каталога.

Минусы: второй aggregate и межагрегатная согласованность; сложнее атомарно публиковать страницу; внешний CMS добавляет инфраструктуру и новый источник истины.

Вывод: возможная будущая граница для Stories и сложных материалов, но излишняя для первой Genre story.

### Универсальная EAV-таблица переводов

Пример: `entity_type + entity_id + field_name + locale + value`.

Плюсы: один механизм для всех объектов.

Минусы: теряется типизация, сложнее обеспечить обязательность и целостность, переименование поля становится миграцией данных, запросы и аудит становятся менее прозрачными.

Вывод: отвергается как преждевременная универсализация.

### Перевод на лету

Хранится один исходный язык, а машинный перевод генерируется при запросе или кэшируется.

Плюсы: быстрое покрытие новых языков и меньше ручной работы.

Минусы: недетерминированный исторический текст, сложная проверка терминологии и источников, зависимость от внешней модели; результат нельзя считать редакционно опубликованным без review.

Вывод: допустимо позже только как draft-предложение для Editor, но не как источник публичного контента.

## Рекомендуемая политика проекта

### Идентификаторы локалей

- Использовать валидные language tags BCP 47, например `ru`, `en`, а при реальной необходимости `en-GB`.
- Не создавать закрытый enum языков в домене.
- Хранить канонизированное представление тега и не добавлять регион или script без содержательной причины.

BCP 47 задаёт стандартную структуру language tag; W3C также рекомендует ссылаться именно на BCP 47 и использовать настолько короткий тег, насколько позволяет смысл.

### Разделение данных

Языконезависимыми остаются:

- стабильный ID и тип сущности;
- структурированные период и географические ссылки;
- enum-коды и направления relations;
- evidence/editorial состояния;
- ссылки на Source, Evidence и MediaAsset.

Локализуются:

- отображаемое название и aliases, когда alias относится к конкретному языку;
- определение и редакционные описания;
- объяснение Claim или Genre relation;
- alt-текст изображения;
- пользовательские labels enum — в UI resources, а не в базе.

Название источника и цитата сохраняются в языке источника. Перевод цитаты является отдельным редакционным значением и не заменяет оригинал.

### Публикация

Рекомендуется разделить жизненный цикл сущности и доступность её языкового варианта:

- принятый `ClassificationConcept` с `kind=genre` остаётся Aggregate Root и владеет общим lifecycle;
- translation является частью этого aggregate и проходит собственную проверку готовности к публикации;
- публикация русского варианта не требует готового английского;
- публичный ответ никогда не выдаёт draft-перевод.

Это уточняет, но не отменяет правило, что доменный статус хранится у context-владельца: оба состояния принадлежат Music Catalog и изменяются через Genre aggregate.

### Минимум для публикации

Для опубликованного языкового варианта Genre рекомендуется требовать:

1. `name`;
2. краткое `definition`.

Период, география, признаки, процесс формирования, relations, examples, dances, Stories, sources и изображение опциональны. Пустое значение не заменяется фиктивным текстом в базе. UI обязан иметь осмысленное empty state.

### Выбор языка и fallback

Рекомендуемый порядок:

1. явно выбранная локаль в URL или настройке пользователя;
2. сохранённый выбор браузера/профиля;
3. HTTP `Accept-Language`;
4. локаль проекта по умолчанию — `ru`.

HTTP определяет `Accept-Language` как предпочтения клиента, а не как гарантированно доступный вариант. Поэтому fallback должен быть политикой приложения.

Рекомендуемый fallback для контента:

```text
requested exact locale → base language → published default locale `ru`
```

Если показан fallback, read contract должен явно передать `requested_locale`, фактический `content_locale` и признак fallback. Интерфейс не должен молча выдавать русский текст как английский.

### Форматирование и поиск

- Даты и числа хранятся в нейтральном виде и форматируются по locale средствами, основанными на Unicode CLDR.
- Поиск выполняется внутри выбранной локали и aliases; межъязыковой поиск относится к отдельной search story.
- Locale-specific slug можно добавить позже. Стабильная identity не должна зависеть от переведённого slug.

## Рекомендация при возвращении локализации в scope

- Создать отдельную localization story после стабилизации одноязычных Genre contracts.
- Миграция существующего контента и обратная совместимость должны стать частью её acceptance criteria.
- Не требовать одновременную готовность всех переводов.
- Проверить отсутствие необработанных `null`, пустых заголовков, несуществующих ссылок и draft-переводов.
- Не проектировать универсальную translation platform для всех будущих aggregates: применить тот же принцип к следующей сущности при появлении её story.

Для физического хранения остаются два разумных кандидата:

1. типизированная `genre_translation` — сильнее целостность, прозрачнее поиск и доменная модель;
2. `genre_content` с одним JSON-документом на локаль — компактнее SQL schema, но слабее DB-инварианты.

Будущая localization story должна потребовать независимую публикацию локалей и отсутствие дублирования Genre, но не предрешать таблицы до проектирования data/API contract. Значимое решение о физической схеме при необходимости фиксируется ADR.

## Требует подтверждения Product Owner

Вопросы не блокируют EPIC-001.

1. Обязательны ли `name + definition` для публикации конкретной локали?
2. При отсутствии запрошенного языка показывать явный русский fallback или возвращать состояние «перевод недоступен»?
3. Нужны ли локализованные URL в первой будущей localization story или их можно добавить отдельным frontend routing/SEO-срезом?
4. Какой кандидат предпочесть для Genre: типизированную translation-таблицу или JSON-документ на локаль?
